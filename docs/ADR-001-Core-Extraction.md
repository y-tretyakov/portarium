# ADR-001: Извлечение portarium-core (Core Extraction)

**Статус:** Accepted  
**Дата:** 22 июля 2026  
**Автор:** Главный Архитектор  
**Версия:** 1.0

## 1. Контекст (Context)

В текущей архитектуре проекта Portarium существует значительное **дублирование кода**:

- Логика сканирования портов (`scanner.rs` в `src-tauri` и `scanner.ts` в `src-tui`)
- Определение фреймворков и dev-портов
- Логирование событий и трафика
- Построение графа соединений
- Обработка процессов (kill/restart)

Это приводит к:
- Высоким затратам на поддержку
- Рискам расхождения поведения между Desktop и TUI
- Сложностям при добавлении новых фич
- Зависимости TUI от внешнего инструмента OpenTUI (Bun + React)

## 2. Проблема (Problem)

Нужно создать **единую кодовую базу** бизнес-логики, чтобы:
- Устранить дублирование
- Сделать код переиспользуемым между TUI, Desktop (Tauri) и CLI
- Упростить тестирование и развитие проекта
- Подготовить основу для замены OpenTUI на Ratatui

## 3. Решение (Decision)

**Создать отдельный Rust crate `portarium-core`** как библиотеку (`lib`), содержащую всю бизнес-логику проекта.

### Целевая структура

```text
portarium/
├── core/                          # ← Новый crate (library)
│   ├── Cargo.toml
│   └── src/
│       ├── lib.rs                 # Публичное API
│       ├── models.rs
│       ├── error.rs
│       ├── config.rs
│       ├── scanner/
│       ├── logger/
│       ├── graph/
│       ├── frameworks/
│       └── service.rs             # Главный фасад
├── tui/                           # Ratatui TUI (будет использовать core)
├── src-tauri/                     # Tauri Desktop (будет использовать core)
├── cli/                           # CLI (будет использовать core)
├── Cargo.toml                     # Workspace
└── docs/
```

### Ключевые принципы реализации

- `portarium-core` — чистая библиотека без side-effects
- Все ошибки через `thiserror` + тип `Result`
- Явный публичный API (`pub use` в `lib.rs`, без wildcard)
- Trait-based платформо-зависимый код (`ScannerBackend`)
- Расширяемость (`FrameworkRegistry` через TOML)
- Полное покрытие тестами (unit + proptest)

## 4. Альтернативы, которые рассматривались

1. **Оставить как есть** — дублирование кода
2. **Вынести в shared TypeScript модуль** — не решает проблему Rust-логики
3. **Создать daemon-сервис** — избыточно на данном этапе
4. **Использовать existing crate** — нет подходящего open-source решения нужного качества

**Выбрано:** `portarium-core` как Rust library.

## 5. Последствия (Consequences)

### Положительные
- Единая истина в коде
- Значительно проще добавлять новые фичи
- Легко тестировать бизнес-логику
- Чистая архитектура для Ratatui и CLI
- Упрощение `src-tauri` (тонкие обёртки)

### Отрицательные / Риски
- Необходимость рефакторинга `src-tauri`
- Время на миграцию TUI
- Нужно аккуратно управлять зависимостями в workspace

### Нейтральные
- Небольшое увеличение времени компиляции (workspace)
